# 셀프 논증 — Klook ClearTrip v2

## 쟁점 1. 예약 정보 통합과 강제 확인 절차의 필요성

**검토 대상:** Screen B — Unified Booking Review

**관련 원칙:** P05(오류 예방), P06(기억보다 인식), P07(유연성과 사용 효율성), P08(미적이고 간결한 디자인)

**논증 방식:** Flutter UI 초안 구현 이후 AI와의 비판적 대화를 통해 기존 설계 가정을 재검토하고 개선 방향을 결정함.

### 1. 내 초기 주장

기존 Klook 앱에서는 Booking Summary, Price Summary, 취소 및 환불 규정 등 예약 관련 정보가 여러 영역에 분산되어 있다. 사용자는 예약 조건을 확인하기 위해 여러 화면을 오가거나 추가 영역을 열어야 한다.

나는 젊은 여행 서비스 이용자에게 시간과 노력의 효율성이 중요하다고 생각하였다. 여행 플랫폼의 본질적인 기능은 사용자에게 편리한 서비스를 제공하는 것이므로, UI/UX 개선을 통해 정보 탐색 비용을 줄일 필요가 있다고 판단하였다.

따라서 Klook ClearTrip v2에서는 날짜, 인원, 가격, 취소 규정 등 핵심 예약 정보를 하나의 Unified Booking Review 화면에 통합하고자 하였다.

### 2. AI의 초기 반론

AI는 정보의 통합이 반드시 인지적 부담의 감소로 이어지는 것은 아니라고 지적하였다.

첫째, 여러 화면에 분산되어 있던 정보를 한 화면에 모두 표시하면 오히려 정보 과부하가 발생할 수 있다.

둘째, 화면 전환 횟수가 감소하는 것과 사용자가 정보를 이해하는 데 필요한 인지적 노력이 감소하는 것은 서로 다른 문제이다.

셋째, 기존 Klook의 정보 분산 방식은 사용자가 필요한 정보만 단계적으로 확인하도록 하기 위한 설계일 가능성도 있다.

따라서 정보 통합 자체만으로 UX 개선 효과를 단정할 수 없으며, 그 효과를 입증할 추가 근거가 필요하다는 반론이었다.

### 3. 나의 재반론 — 효율성의 중요성

나는 젊은 사용자들이 시간 비용과 노력 비용을 중요하게 고려한다는 점을 강조하였다.

Klook은 여행 서비스 플랫폼이므로, 사용자가 예약에 필요한 정보를 더 적은 노력으로 확인할 수 있도록 하는 것이 서비스 품질 향상에 기여한다고 주장하였다.

다만 이 주장은 목표 사용자에 관한 설계 가정이며, 실제 시간 절약 및 사용자 유지율 개선 효과를 검증한 결과는 아니다.

### 4. AI의 추가 반론 — 효율성과 정확성의 충돌

AI는 빠른 예약이 반드시 좋은 예약 경험을 의미하지는 않는다고 반박하였다.

예약 과정이 빨라져도 사용자가 잘못된 날짜를 선택하거나 환불 불가 조건을 놓친다면, 사후 수정 및 문제 해결에 더 많은 비용이 발생할 수 있다.

또한 이미 Screen A에서 예약 조건을 선택한 사용자가 Screen B에서 동일한 정보를 다시 확인하고 Checkbox까지 선택해야 한다면, 오히려 불필요한 단계가 추가될 수 있다고 지적하였다.

이에 따라 AI는 독립적인 확인 화면을 유지해야 하는지, 기존 예약 과정에 간단한 요약 영역을 통합하는 편이 더 효율적인지 검토할 것을 요구하였다.

### 5. 나의 재반론 — 정확성과 효율성의 병행

나는 기존 Klook에도 사용자가 예약 정보를 확인할 수 있는 기능이 이미 존재한다고 설명하였다.

따라서 v2의 목적은 정확성을 처음부터 새롭게 구현하는 것이 아니라, 기존에 제공되던 확인 기능을 유지하면서 정보 접근 효율성을 개선하는 데 있다고 주장하였다.

또한 예약 확인 화면은 소비자와 플랫폼 양측에 중요한 확인 기회를 제공한다. 따라서 효율성을 높인다는 이유만으로 확인 절차를 삭제하는 것은 적절하지 않다고 판단하였다.

내가 추구하는 개선 방향은 단순한 단계 축소가 아니라 **정확성과 효율성의 동시 향상**이다.

### 6. AI의 심화 반론 — 강제 Checkbox의 실효성

AI는 강제 Checkbox가 실제로 오류를 예방하는지에 대해 다음과 같이 비판하였다.

- **P05 오류 예방:** 사용자가 Checkbox를 선택했다고 해서 날짜나 환불 조건을 정확하게 이해했다고 보장할 수 없다.
- **P07 유연성과 사용 효율성:** 모든 사용자에게 동일한 확인 절차를 강제하면 숙련된 사용자의 작업 효율이 낮아질 수 있다.
- **P08 미적이고 간결한 디자인:** 이미 화면에 제공된 정보와 동일한 내용을 반복하는 확인 문구는 불필요한 시각적·상호작용적 부담이 될 수 있다.

AI는 따라서 모든 상품에 동일한 확인 문구를 적용해야 할 이유가 충분하지 않다고 지적하였다.

### 7. 나의 재반론 — Checkbox의 역할 재정의

나는 Checkbox의 목적이 단순히 사용자가 확인 버튼을 한 번 더 누르도록 하는 것이 아니라고 설명하였다.

핵심 목적은 사용자가 예약을 확정하기 전에 **환불 불가, 사용 날짜 제한 등 실제 손실로 이어질 수 있는 조건을 명확하게 인지하도록 하는 것**이다.

따라서 Checkbox를 일반적인 완료 확인 수단보다는 중요한 예약 위험을 고지하고 사용자의 명시적 인지를 확인하는 장치로 이해하는 것이 적절하다고 판단하였다.

다만 이러한 확인 절차는 법적 책임의 자동적인 면제를 의미하지 않는다.

### 8. 최종 설계 결정

**최종 판단: 수정**

AI의 반론을 검토한 후 다음과 같이 설계 방향을 확정하였다.

1. **Unified Booking Review 화면을 유지한다.** 예약 조건을 통합하여 사용자가 여러 영역을 반복적으로 탐색하지 않도록 한다.
2. **강제 Checkbox를 유지한다.** 중요한 예약 위험을 명시적으로 확인할 수 있도록 한다.
3. **Checkbox 문구를 상품 조건에 따라 동적으로 변경한다.** 환불 불가 상품에는 환불 제한을, 지정 날짜 상품에는 사용 날짜 제한을, 무료 취소가 가능한 상품에는 실제 취소 가능 기한을 정확하게 표시한다.
4. **상세 규정은 필요할 때 확인하도록 한다.** 핵심 위험은 기본 화면에 표시하되, 긴 정책 설명은 별도 상세 영역에 배치하여 정보 과부하를 방지한다.
5. **조건 수정 경로를 유지한다.** 사용자가 잘못 선택한 날짜나 인원을 확인한 경우 이전 단계에서 수정할 수 있도록 한다.

이 결론은 기존 설계를 모두 폐기하지 않고, AI의 비판을 반영하여 확인 절차의 목적과 정보 표현 방식을 구체화한 결과이다.

### 9. 근거 및 원칙 연결

| Nielsen 원칙 | 설계 적용 |
|---|---|
| P05 — Error Prevention | 상품별 중요한 위험 조건을 명확하게 알리고 예약 확정 전 확인 기회를 제공 |
| P06 — Recognition Rather Than Recall | 날짜, 인원, 가격 등 핵심 정보를 예약 확인 화면에서 다시 확인 |
| P07 — Flexibility and Efficiency of Use | 중복 정보 탐색을 줄이되 확인 절차의 추가 비용도 고려 |
| P08 — Aesthetic and Minimalist Design | 핵심 조건과 상세 정책의 정보 위계를 구분 |

### 10. Before / After 및 검증 상태

**Before — 초기 v2 설계:** 통합 예약 확인 화면과 일반적인 강제 확인 Checkbox를 사용한다.

**After — AI 논증 이후 수정 결정:** 통합 확인 화면과 강제 Checkbox를 유지하면서, 상품별 실제 예약 위험을 반영하는 동적 문구로 변경한다.

**구현 상태:** 위 내용은 논증을 통해 확정한 설계 변경안이다. 실제 Flutter 구현 여부와 전후 화면 비교는 별도로 확인하여 기록한다.

**검증 한계:** 사용자 테스트를 통한 작업 완료 시간, 오류율, 위험 인지율 개선 효과는 아직 측정하지 않았다. 따라서 UX 개선 효과는 검증된 결과가 아닌 설계 가설로 제시한다.
